03 / DATABASE DESIGN & ERD Slide 4 / 11

Relational Data Architecture

Four core normalized tables with explicit foreign keys and cascade rules.

users Table

Primary Table

Fields: id, fullName, email, password, role, isActive, createdAt, updatedAt

Roles: ADMIN, AGENT, CLIENT. Passwords hashed using bcrypt (10 rounds) and hidden via select: false.

properties Table

Listing Portfolio

Fields: id, title, description, propertyType, listingType, price, location, address, agentId...

Indexed by location, price, and status. Foreign key agentId -> users(id) ON DELETE SET NULL.

inquiries Table

Communication Pipeline

Fields: id, clientId, propertyId, assignedAgentId, subject, message, contactNumber, status...

Status lifecycle: PENDING -> CONTACTED -> QUALIFIED -> CLOSED.

appointments Table

Viewing Scheduler

Fields: id, propertyId, clientId, agentId, appointmentDate, appointmentTime, status, notes...

Enforces schedule conflict prevention and validates that appointments cannot be booked in the past.

04 / DATABASE NORMALIZATION (3NF) Slide 5 / 11

Relational Normalization Proof

Defensible academic structure eliminating anomalies and redundancy.

First Normal Form (1NF) — Atomicity

Every column holds strictly atomic (indivisible) values. No repeating groups or serialized multi-value strings exist. Surrogate primary keys (id) uniquely identify each record.

Second Normal Form (2NF) — Full Functional Dependency

All tables are in 1NF. Because all tables use single-attribute surrogate keys (id), no partial functional dependencies can mathematically exist. Every non-key attribute depends entirely on the whole key.

Third Normal Form (3NF) — No Transitive Dependencies

All tables are in 2NF. No non-key attribute depends on another non-key attribute ($X \to Y$ and $Y \to Z$). Client names, agent contacts, and property locations are never duplicated inside appointments or inquiries; they are dynamically resolved through foreign key joins.

06 / AUTHENTICATION & SECURITY Slide 7 / 11

Stateless JWT & Role-Based Guards

Multi-layered security protecting administrative and business routes.

JWT Authentication Workflow

Upon successful login at POST /api/auth/login, the backend issues a cryptographically signed JWT containing claims (sub: userId, email, role). Clients present this in the Authorization: Bearer <token> header on all protected requests.

Payload: { sub: 1, email: "admin@estatecore.local", role: "ADMIN" }

Role-Based Access Control (RBAC)

Enforced by RolesGuard and custom @Roles() decorator. Public registration strictly forces the user to the CLIENT role; administrative privilege assignment is restricted to verified administrators.

@Roles(UserRole.ADMIN, UserRole.AGENT)
async createProperty(@Body() dto, @CurrentUser() user)

Data Flow Across System Layers

Tracing POST /api/properties through every architectural layer.

1. Postman / Client → 2. PropertiesController → 3. PropertiesService → 4. TypeORM Repository → 5. MySQL 8.4 Database

Controller Handling:

Interprets HTTP request, verifies JwtAuthGuard and RolesGuard, runs DTO validation pipe, and passes typed data to the service.

Business Logic Service:

Enforces ownership rules: forces agentId = user.id if the creator is an AGENT. Prevents unauthorized assignment.

Repository Mapping:

TypeORM converts TypeScript entity to parameterized SQL INSERT INTO properties (...) VALUES (...).

ACID Database Execution:

MySQL commits transaction to disk volume and returns auto-generated surrogate key id back out to the response.
